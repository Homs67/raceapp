Overview

Dev workflow

How to build, test and run the app — mostly without a car, an adapter or a RaceBox in reach — and the conventions and gotchas worth knowing before your first change.

Build & test

Xcode 26, iOS 17 deployment target. Bundle id com.goodproductslab.raceApp.

Packages — fast, on the Mac, no Simulator

cd Packages/SessionKit && swift test     # ~107 tests
cd Packages/ObdKit     && swift test     # ~63
cd Packages/RaceBoxKit && swift test     # ~55
cd Packages/BleKit     && swift test     # ~6

App

xcodebuild -project raceApp.xcodeproj -scheme raceApp \
  -destination 'platform=iOS Simulator,name=iPhone 17' build

xcodebuild test -project raceApp.xcodeproj -scheme raceApp \
  -destination 'platform=iOS Simulator,name=iPhone 17' -only-testing:raceAppTests
Note

The app target uses synchronized file groups: anything you add under raceApp/ is compiled (or bundled) automatically — no project-file edits. Because resources are flattened, bundled JSON and fonts are loaded by bare file name.

Every hardware source has a fake that drives the real pipeline — sessions, decoders, recorder, dashboard — so almost everything can be worked on in the Simulator.

What the Simulator can't do
  • No CoreMotion device motion — phone car-frame G, and anything that depends on handling the phone, can only be checked on a device.
  • No Bluetooth — real adapters and RaceBoxes need a device. tools/racebox-probe.swift builds a small macOS app that talks to a real RaceBox from a Mac.
  • simctl io screenshot captures the unrotated framebuffer — rotate the image yourself for landscape.

Conventions

  • Never a fake zero. Stale or missing data is nil and renders as —. Read the bus through fresh(…, maxAge:).
  • Recorded truth stays honest about its source. Mirrors for display go through publishLive; one owner per canonical channel at a time.
  • Monotonic time for every sample; wall-clock only where it's explicitly needed.
  • Logic in packages, wiring in AppModel. Prefer pure types fed one sample at a time.
  • Verify numeric code against real data. Replay a real drive and score the result with an independent sensor before trusting a new parameter.
  • Comments explain why. The codebase leans on comments that record the decision and the evidence ("a steady 0.8 g corner decayed to 0.07 g…"). Keep that up.
