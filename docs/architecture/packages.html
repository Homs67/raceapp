Overview

Swift packages

Four local Swift packages hold every piece of logic that doesn't need a screen. They build and test on the Mac with swift test — no Simulator, no device, no car — which is why the maths in them is trustworthy.

Why packages

Rule · what goes where

In a package: protocols, decoders, file formats, algorithms — anything you can describe with inputs and outputs. Prefer pure functions and small stateful types fed one sample at a time.
In the app: SwiftUI views, and the controllers that own a live connection or iOS framework object and wire things to the bus.

The practical payoff: a lap timer, a G-force calibrator or a packet parser can be replayed against a recorded real drive in a unit test. Several bugs on this project were found exactly that way, and several algorithm parameters were chosen by replaying a real drive and scoring the result.

BleKit

Bytes in, bytes out. Everything above it is protocol-specific; BleKit knows nothing about OBD or RaceBox beyond a profile describing how to find and talk to a class of device.

FileResponsibility
BleTransport.swiftThe transport protocol: connect, write, and an incoming byte stream. Real hardware and fakes both conform.
BleDeviceProfile.swiftService/characteristic UUIDs and name filters per device class (.elm327, .raceBox), plus the CoreBluetooth restore identifier.
CoreBluetoothTransport.swiftThe real implementation: one CBCentralManager per profile, scanning, connection, state restoration, write-with/without-response.
ReplayTransport.swiftScripted fake: canned responses delivered in small chunks, exercising reassembly exactly like a real BLE link. Used by tests.

ObdKit

FileResponsibility
Elm327Session.swiftThe ELM327 command/response conversation: AT init, prompt detection, response accumulation across BLE chunks.
ObdChannel.swiftThe PIDs we know: mode-01 PID number, unit, and the default fast and slow loops.
PidDecoder.swiftPure SAE J1979 formulas: response bytes → engineering value.
PidPoller.swiftFast/slow loop scheduler. Drops channels the ECU answers NO DATA for; never dies on one bad response.
ObdConnectionState.swiftThe connection state machine as data — every state maps 1:1 to a UI status string.
CanSignal.swiftRaw CAN frame parsing and per-car signal maps (CanSignalMap.mazdaND): frame ID + decode closure.
CanMonitorSession.swiftELM327 monitor mode: diagnostic capture, the live stream used while recording (round-robin over frame IDs, OBD interlude), and discovery runs.
CanCorrelator.swiftSignal discovery: correlates every byte of every broadcast frame against OBD ground truth to propose decoders.
SimulatedAdapterTransport.swiftA fake Veepeak that speaks enough ELM327 to drive the whole real pipeline. Powers "Try with demo data".
DemoDrive.swiftWhat a demo source must supply (RPM, speed, throttle) and an open-road drive model.
BleKitCompat.swiftType aliases kept after the transport moved to BleKit.

RaceBoxKit

FileResponsibility
RaceBoxPacket.swiftThe UBX frame: B5 62 · class · id · length · payload · checksum. A streaming parser that reassembles packets split across notifications.
RaceBoxDataMessage.swiftDecodes the 80-byte data message: position, speed, heading, accuracies, fix flags, G-force, rotation rate, power, GNSS time.
RaceBoxCommand.swiftTyped commands and replies: recording status/config/state, memory download, erase, unlock.
RaceBoxSession.swiftActor that owns a connected device: routes packets to the live stream, the history (memory download) stream, or a waiting command; tracks link health.
RaceBoxDevice.swiftModel detection (Mini / Mini S / Micro), capabilities, firmware version, Device Info.
RaceBoxSelfTest.swift"Is it working?" as a list of pass/fail checks for the debug screen.
RaceBoxSimulator.swiftEncoder (the inverse of the decoder) and a simulated device: live data, command replies, and a synthetic memory dump and erase.
