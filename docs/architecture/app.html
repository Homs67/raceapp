raceApp architecture Updated October 2026
Overview

App layer

The raceApp target is SwiftUI views plus a handful of controllers that own live connections and iOS framework objects. One object, AppModel, creates them all and wires them together.

Launch

  1. raceAppApp.swift creates a single AppModel, puts it in the SwiftUI environment, forces dark mode, and calls model.onLaunch().
  2. onLaunch() recovers interrupted sessions, requests sensor permissions, starts phone sensors publishing to the bus, starts OBD discovery, and auto-connects a remembered RaceBox. In DEBUG it also honours launch arguments such as -demo.
  3. ContentView.swift is a tab bar: Sessions (SessionsView) and Tracks (TracksView). While a session records, the dashboard (DashboardPagerView) covers everything as a full-screen cover; Settings and Debug are sheets.
  4. Scene-phase changes go to AppModel.scenePhaseChanged, which re-checks permissions, reconnects devices on foreground, and switches sensors into background recording mode.

raceApp/Model/AppModel.swift is the single best file to read for the shape of the app. It is @MainActor @Observable and owns:

Cross-component behaviour is wired here with closures rather than by components knowing about each other. For example:

// RaceBox → phone sensors: the logger owns position and car-frame G while it streams
raceBox.onPositionFix = { [sensors] mps, course, t in
    sensors.ingestExternalFix(speed: mps, course: course, at: t)
}
raceBox.onMotionSample = { [sensors] t in sensors.noteExternalMotion(at: t) }

// Recording stop → tidy up camera, metrics, sensors, and the CAN stream
recording.onRecordingDidStop = { [weak self] in … }

If you're adding a feature that needs two controllers to cooperate, wire it in AppModel the same way.

Concurrency rules

The app target is compiled with SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor (Swift 5 language mode, iOS 17 deployment target). Every type in raceApp/ is main-actor isolated unless it says otherwise. The packages are not — they're explicit about isolation.

  • Sources publish from any thread. Bluetooth and sensor callbacks never hop to the main actor to publish; TelemetryBus is lock-based for that reason.
  • Long-lived mutable state that crosses threads is an actor: SessionRecorder, SessionWriter, RaceBoxSession, RaceBoxMemoryImporter.
  • PhoneSensorSuite uses locks because CoreMotion and CoreLocation deliver on different queues and calibration state is shared between them.
  • UI reads snapshots, never live mutable state from another thread.
Gotcha · back-deployed isolated deinit

On an iOS 17 target with main-actor default isolation, a class's deinit is routed through a back-deployment shim that can abort in malloc when the object is released. It crashed every DashboardStore test. Short-lived @MainActor classes that don't need the main actor to tear down declare nonisolated deinit {} — you'll see it on DashboardStore, DashboardEditController, ToolbarVisibility and DashboardLiveFeed.
